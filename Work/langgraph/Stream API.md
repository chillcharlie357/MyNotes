# 使用LangGraph SDK Streaming API进行远程代理执行：绕过直接Runnable调用的协议、模式与实现

## I. 战略背景：从本地调用到远程客户端流式传输的架构转型

### 1.1 架构范式转变：本地编译与远程部署

LangGraph是一个低级别的编排框架和运行时环境，专注于构建、管理和部署持久化、有状态的代理程序 [1]。在将基于LangGraph构建的复杂代理从开发环境转移到生产环境时，其与图的交互方式必须从传统的本地执行模式转向基于LangGraph SDK的远程客户端流式传输模型。

用户明确要求避免使用源自LangChain Runnable接口的方法，例如那些由本地编译图或更高层级的`RemoteGraph`抽象暴露的方法（如`remote_graph.invoke()`或`remote_graph.stream()`） [2]。这一约束意味着架构设计必须转向直接的、低层级的API交互，即通过`langgraph_sdk`提供的客户端方法 [3]。

本地执行模型通常使用`graph.compile().invoke()`或`.stream()`，其特征是执行在进程内发生，且具有短暂性 [1]。状态持久性（如果需要）依赖于本地配置的检查点机制。相比之下，远程执行模型（LangSmith部署API）将代理视为一个具有持久性的有状态服务。在这种远程架构中，LangSmith Agent Server管理着核心基础设施：通过`Assistants`管理版本化的图配置，通过`Threads`管理会话状态和记忆，并通过`Runs`记录和控制执行实例 [3, 4]。

将架构选择转移到SDK层（即`client.runs.stream`）至关重要，因为它强制架构师明确承担了管理持久状态上下文（`thread_id`）的责任。Runnable接口（如`RemoteGraph.stream()`）虽然方便，但可能会抽象掉确保企业级持久性所需的 `thread_id`。通过直接使用SDK层 API，客户端将每次执行显式地与一个预先存在的或新创建的 `thread_id` 绑定 [3]。这种从抽象到显式控制的转变，确保了状态的耐用性和会话的连续性，是满足长期运行、状态恢复以及人机协作（Human-in-the-Loop）等生产系统要求的关键 [1, 5]。

### 1.2 LangGraph SDK客户端架构概述

为了高效地实现远程流式传输，必须利用LangGraph SDK提供的客户端工具。SDK提供了同步客户端（`SyncLanggraphClient`）和异步客户端（`LangGraphClient`） [4, 6]。鉴于流式操作涉及长时间的网络连接以及对连续事件块的异步处理，使用异步的`LangGraphClient`是实现高性能和非阻塞流式传输的架构选择。

`LangGraphClient`将API交互组织为围绕核心资源的集合：`assistants`管理图的配置，`threads`处理会话上下文，而`runs`控制图的单个调用 [4]。流式传输逻辑完全集中在`client.runs`客户端中。

在网络基础层面，SDK构建在`HttpClient`之上，这是一个对`httpx`异步客户端的封装 [4]。这个客户端抽象层负责处理额外的错误消息和内容处理，使其能够可靠地管理用于长寿命流式连接所必需的特定协议。

## II. 建立远程流式传输的基础

远程流式传输的启动依赖于清晰、持久的上下文定义，包括已部署代理的配置和当前会话的状态。

### 2.1 客户端初始化与安全连接管理

客户端初始化遵循标准的SDK模式：通过`from langgraph_sdk import get_client`导入所需函数，然后通过指定远程部署的URL实例化异步客户端：`client = get_client(url=<DEPLOYMENT_URL>)` [3]。

在生产集成中，连接到远程LangSmith部署通常需要安全的认证机制。虽然研究资料中未详述，但连接到远程URL隐含要求使用API密钥等凭证，这些凭证通常通过环境配置或客户端显式参数传递，以保障对核心资源（如`Assistants`和`Threads`）的访问安全。

### 2.2 先决条件：定义部署和会话上下文

在调用流式传输方法之前，必须准备好两个核心的持久化标识符，它们共同为远程执行提供了上下文：

1. **助理标识（`assistant_id`）：** 该参数明确指定了要执行的已部署图配置 [3]。它将流式请求链接到Agent Server上托管的特定、版本化的代理逻辑，从而起到了版本控制的作用，由`AssistantsClient`进行管理 [4]。
    
2. **线程标识（`thread_id`）：** 这是远程流式传输中的强制性状态上下文。必须通过`client.threads.create()`预先建立一个Thread，并获取其`thread_id` [3]。Thread封装了完整的会话状态历史，是实现持久性、执行恢复和多轮交互的关键 [1]。
    

**持久性架构中的状态检查点引用**

LangGraph的“耐用执行”能力意味着运行可以通过故障并从中断点恢复 [1]。在远程服务架构中，这种耐用性是通过将每次执行（`Run`）与一个持久的存储键（`Thread`）关联来实现的。`thread_id`在本质上充当了分布式状态的检查点标识符。

SDK通过要求在调用 `client.runs.stream(thread_id, assistant_id,...)` 时提供这些标识符，强制了这种耦合 [3]。客户端集成逻辑必须确保会话的连续性：对于新会话，创建 `thread_id`；对于正在进行的会话，检索并安全地维护该 `thread_id`。这种显式的状态耦合对于需要人机协作的工作流至关重要，因为它可以随时检查、修改和恢复代理状态 [5]。

### 2.3 远程执行原语及其作用

下表列出了LangGraph SDK客户端中的核心资源及其在构建远程、有状态流式会话中的作用：

远程执行原语和它们的作用

|   |   |   |   |
|---|---|---|---|
|**原语**|**LangGraph SDK 属性**|**定义**|**流式传输要求**|
|Assistant（助理）|`client.assistants`|版本化的图配置和逻辑。|必需 (`assistant_id`)|
|Thread（线程）|`client.threads`|耐用的、有状态的会话上下文和内存。|必需 (`thread_id`) [3]|
|Run（运行）|`client.runs`|图的单个调用实例。|主要API焦点 (`runs.stream`)|
|Store（存储）|`client.store`|接口访问持久化、共享数据存储（隐式检查点） [4]|由Thread隐式使用|

## III. `client.runs.stream()` 的机制：绕过本地执行

`client.runs.stream()`是实现远程流式交互的核心方法。它提供了一种基于事件驱动的低延迟机制，用于实时跟踪代理执行的进度和输出。

### 3.1 Streaming API的详细签名和必需参数

该方法被设计为异步调用，要求三个核心参数：`thread_id`、`assistant_id`和`input`负载 [3]。`input`负载必须符合已部署图的预期输入模式。

除了这些核心上下文参数外，还提供了控制流式传输粒度的可选参数，其中最重要的是`stream_mode`（控制输出内容）和`stream_subgraphs=True`（控制输出范围） [3]。

### 3.2 异步工作流：利用 `async for chunk in...`

Python实现利用异步迭代器，即`async for chunk in client.runs.stream(...)` [3]。这种模式对于流式API至关重要，因为它允许客户端应用程序在不阻塞主线程的情况下，持续读取和处理从网络连接推送的事件。每次迭代都会产生一个数据块，客户端必须根据配置的`stream_mode`来解析和处理该数据块。

### 3.3 流式传输选项分析：启用子图输出 (`stream_subgraphs=True`)

LangGraph支持将复杂代理工作流分解为嵌套图（子图）。默认情况下，流式传输可能仅报告父图层面的状态变化。通过设置 `stream_subgraphs=True`，可以确保来自内部子图的输出也包含在事件流中 [3]。

在远程异步环境中，当代理涉及复杂的条件分支和迭代循环（如ReACT）时，追踪执行流对于诊断和调试至关重要。节点运行过程中可以访问运行时上下文，包括配置（`config`）和运行时对象（`runtime`），其中包含像`thread_id`和`stream_writer`这样的信息 [7]。能够流式传输子图输出 [3]，结合细粒度流模式（如`messages`和`debug`） [8]，提供了对远程代理内部“超级步骤” [7] 和计算的必要可见性。这种对可观察性的强调是任务关键型代理部署中的架构考量。

## IV. 高级流式传输模式：粒度与数据解析

`stream_mode`参数是SDK控制数据流内容的中心机制，允许工程师权衡数据完整性和网络效率 [9]。SDK支持多种模式，每种模式都适用于不同的应用场景。

### 4.1 `stream_mode` 配置的范围

LangGraph SDK支持五种主要流式模式：`values`（完整值）、`updates`（增量更新）、`messages`（LLM消息/Token）、`custom`（自定义数据）和`debug`（详细跟踪） [8]。

**多模式流式传输：** SDK支持通过传入模式列表（例如，`stream_mode=["updates", "custom"]`）来同时流式传输多个模式。在这种情况下，输出的数据块将作为元组的形式传输：`[mode, chunk]`，其中`mode`是流模式的名称，`chunk`是该模式传输的具体数据 [8]。

### 4.2 模式深度分析 1：状态增量 (`updates`)，实现效率

机制： updates模式只返回在节点完成执行或超级步骤结束之后，应用于状态对象的增量更改（Deltas） [3, 9, 10]。

实践： 这是构建生产级流式接口的推荐模式，它以最低的带宽消耗提供实时状态通知。客户端应用程序必须实现逻辑以顺序应用这些增量，从而重建当前图状态。

### 4.3 模式深度分析 2：完整状态快照 (`values`)，实现可见性

机制： values模式在每次执行步骤后，返回图的完整、当前状态的快照 [9, 10]。

实践： 尽管这种模式导致更高的带宽消耗，但它对于人机协作、详细日志记录和调试是无价的，因为它在每个检查点都提供了完整的上下文，无需客户端进行增量聚合。

### 4.4 模式深度分析 3：实时LLM Token传输 (`messages`)

机制： messages模式专用于从图中的任何位置（节点、工具、子图）逐个Token地流式传输LLM的输出 [8]。它与内部支持流式传输的astream和astream_events方法密切相关 [10]。

输出结构分析： messages模式的流式输出被标准化为一个元组：[message_chunk, metadata] [8]。metadata包含了关键的执行细节，如输出产生的源节点或工具，这对于构建精确归因的聊天UI至关重要。

### 4.5 模式深度分析 4：自定义和调试流

Custom（自定义）模式： 允许开发人员通过访问节点的runtime配置中的stream_writer对象，从节点函数或工具内部流式传输任意、用户定义的数据 [7, 8]。这对于发送进度指示、内部工具操作日志或非状态相关的状态更新很有用。

Debug（调试）模式： 提供了最细致、低级别的执行跟踪，是进行深入架构分析和精细调整代理循环的理想工具 [8]。

**LangGraph 流式传输模式的粒度分析**

|   |   |   |   |   |   |
|---|---|---|---|---|---|
|**流模式**|**数据内容**|**输出结构**|**效率**|**主要用例**|**流式传输来源**|
|`updates`|增量状态变化（Deltas）|Dict/状态增量|高|生产流式传输，带宽优化 [3]|超级步骤/节点结束|
|`values`|完整图状态快照|完整状态对象|低|调试，完整状态审计 [9]|超级步骤/节点结束|
|`messages`|LLM Tokens + 元数据|元组：`[chunk, metadata]`|响应性最高|实时聊天UI，Token显示 [8]|内部节点/工具执行|
|`custom`|任意用户定义数据|用户定义数据|灵活|进度信号，自定义事件 [8]|节点运行时 (`stream_writer`) [7]|
|`debug`|详细执行跟踪|跟踪/事件数据|最低|代理优化，深度追踪 [8]|内部 LangGraph 运行时|

## V. 协议分析：服务器发送事件（SSE）与客户端处理

LangGraph SDK流式传输机制的关键在于其对底层网络协议的选择，即服务器发送事件（SSE）。

### 5.1 HTTP 流式传输（SSE）在LangGraph事件传输中的应用

LangGraph Agent Server使用服务器发送事件（SSE）格式，通过标准HTTP协议提供事件流 [11]。SSE建立了一个单一的、持久化的HTTP连接，允许服务器异步地将格式化事件（`data: {json}\n\n`）推送到客户端 [11]。

LangGraph SDK的`LangGraphClient`通过其内置的`HttpClient`封装，有效地管理了这种SSE连接，负责解析SSE标准流并将数据块转换为Python对象，供客户端的`async for`循环消费。

### 5.2 比较分析：SSE vs. WebSocket

在代理状态流式传输的场景中，SSE相比于WebSocket具有特定的架构优势 [11]：

1. **单向最优性：** 代理执行流程的特点是高频率的服务器到客户端输出（状态更新、Tokens）和间歇性的客户端到服务器输入（人机协作指令）。SSE是“单向最优”的，其开销低于专为全双工、持续双向通信设计的WebSocket。
    
2. **运维优势：** SSE协议基于标准HTTP，无需连接升级，简化了防火墙和代理的配置。此外，SSE内置了客户端自动重连机制，提高了连接的鲁棒性 [11]。
    
3. **架构解耦：** 选择SSE协议表明，尽管代理执行是有状态和持久的（需要持续输出流），但任何客户端控制指令（如中断或修改状态）都可以通过使用 `thread_id` 的单独标准 REST API 调用来处理 [3]。这种解耦提高了流式传输本身的稳定性。
    

### 5.3 技术实现：SDK客户端的SSE解析管理

`LangGraphClient`依靠其`HttpClient`封装层来维护SSE连接。该客户端必须持续监控流，容忍网络波动，并按SSE标准解析事件流。它将网络事件转换为应用程序可以处理的异步数据块，这是实现高性能远程代理交互的关键底层技术。

## VI. 生产系统中的架构影响与最佳实践

### 6.1 性能优化：选择最优的流式模式

在生产系统中，流式模式的选择直接影响用户体验和运营成本。

- **低延迟UI的最佳实践：** 为了提供实时、响应式的体验，应结合使用`messages`模式进行即时LLM Token显示，并使用`updates`模式来获取必要的、低带宽的状态变化通知（例如，节点转换或工具调用的完成）。
    
- **审计与分析实践：** `values`或`debug`模式虽然提供了全面的上下文，但由于数据开销大，应仅限于故障排除或关键流程审计使用，不宜作为常态化的生产流。
    

### 6.2 整合流式输出到前端/UI层

当后端服务使用Python SDK与远程Agent Server交互并需要将输出推送到Web前端时，该后端服务通常需要充当代理。它将异步的SDK流（SSE格式）转换为前端可消耗的格式（可能是另一个SSE端点或WebSocket）。

客户端状态管理是关键。前端客户端必须能够正确处理多模式流式传输的元组输出 `[mode, chunk]` [8]。如果采用 `updates` 模式，前端必须包含一个状态聚合器，该聚合器顺序地、正确地应用收到的状态增量，以确保客户端对代理的当前状态保持准确的同步。

### 6.3 安全部署与认证要求

生产集成必须确保用于连接 LangSmith 部署 API 的 API 密钥和客户端凭证得到安全处理。部署架构应确保访问控制机制基于 `assistant_id` 的权限和与执行线程关联的用户进行管理，以支持多租户和隔离需求 [3]。

### 6.4 耐久性与状态检查点在远程执行上下文中的作用

远程流式传输的整个过程都以持久状态（`thread_id`）为锚点 [3]。这种设计保证了即使客户端或网络中断，执行状态也通过服务器端的检查点机制得以保留 [1]。客户端可以在网络恢复后，通过对现有`thread_id`发起新的运行请求来实现恢复，这一能力是构建复杂、中断/恢复式工作流（如人机协作）的基石 [5]。

## VII. 结论与总结

本报告全面阐述了使用 LangGraph SDK 的 Streaming API (`client.runs.stream()`) 实现远程代理执行的技术方法。这一方法要求系统架构师放弃本地的 `Runnable` 抽象，转而采用低级别的 SDK 接口，并显式管理核心持久性标识符 (`thread_id` 和 `assistant_id`)。

通过这一架构选择，应用程序获得了 LangGraph 远程部署的全部优势：耐用执行、精细的流式传输控制以及对底层执行事件的深入可见性。LangGraph SDK 对异步操作和 SSE 协议的利用，确保了在生产环境中实现高性能、可观察和高弹性的代理系统。

**关键技术要点总结：**

1. **强制的状态管理：** 远程流式传输的核心在于必须先创建并使用 `thread_id` [3]，确保每次运行都与一个持久的状态上下文相关联，实现故障恢复和会话连续性 [1]。
    
2. **细粒度输出控制：** `stream_mode` 参数提供了从高效率的 `updates` 模式到实时用户体验所需的 `messages` 模式的全面控制，允许工程师根据应用需求精确调整带宽和响应速度 [8]。
    
3. **协议优化：** 服务器发送事件（SSE）协议被选为流式传输机制，它利用标准 HTTP 的简单性和内建的重连优势，为代理状态的单向推送提供了优化且可靠的通道 [11]。
    

对于致力于构建和部署企业级 AI 代理的工程师而言，深入理解 `client.runs.stream()` 的工作原理及其对持久状态的依赖，是实现可靠、高效和可追溯的 AI 工作流的必要条件。
